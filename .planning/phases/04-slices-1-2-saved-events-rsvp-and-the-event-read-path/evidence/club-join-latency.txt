## 4. Indexes

clubs_pkey | CREATE UNIQUE INDEX clubs_pkey ON public.clubs USING btree (id)
idx_events_club_id | CREATE INDEX idx_events_club_id ON public.events USING btree (club_id)

- events.club_id IS indexed: idx_events_club_id (btree), declared in supabase/migrations/20260915214553_baseline.sql:1476.
  Correction to the research wording: the index comes from the Phase 3 baseline (03-04), not from 03-05's
  20260915230000_fk_indexes_and_policy_gaps.sql, whose header says it deliberately does not re-issue baseline indexes.
- For THIS embed direction (event -> its one club) the lookup is served by clubs_pkey, as the plan above shows
  (Index Scan using clubs_pkey, one probe per event row). idx_events_club_id serves the reverse direction
  (a club's events) and the FK's ON DELETE SET NULL.

## 5. Verdict (numbers, not adjectives)

- Saved-events (star -> star + embed): median 0.89 ms -> 1.24 ms, difference +0.34 ms per request (N=20 each, local stack).
- List routes (ten -> fifteen embed columns): median 0.93 ms -> 1.10 ms, difference +0.17 ms per request (N=20 each, local stack).
- Scale caveat: the seed has 5 events (2 approved) and 5 clubs, so these medians measure fixed per-request
  overhead plus a two-row join. The per-row cost in Postgres is one clubs_pkey probe (section 3); at production
  page sizes (limit 20-50) the join adds one PK probe per returned row, not a scan. This measurement does not
  stand in for a production timing; Phase 8 (performance) owns that.
