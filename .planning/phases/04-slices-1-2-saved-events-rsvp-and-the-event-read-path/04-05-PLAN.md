## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| browser → save/rsvp/saved-events/calendar/friends handlers | Session cookie in, per-user data out |
| handler → Postgres under RLS | Every read and write uses the cookie-bound server client; RLS is the second ring |
| request body user_id → authorization decision | RSVP POST/DELETE compare a body field to the session user |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04-05-01 | Spoofing | Authentication through the seam | mitigate | `createRequestContext()` uses the revalidating user read (never a session read); `requireUser` fails closed by construction; PRESERVE suites pin the 401 bytes including the auth-error-with-null-user case |
| T-04-05-02 | Elevation of Privilege | RSVP body user_id differing from the session | mitigate | The 403 comparison is kept verbatim and pinned by rsvp.test.ts and the PRESERVE suite |
| T-04-05-03 | Information Disclosure | RSVP GET made anonymous-readable or made authenticated by accident | mitigate | Prohibition: GET gains no guard; PRESERVE pins anonymous counts with `user_rsvp: null` (the underlying policy is F-011, Phase 5) |
| T-04-05-04 | Elevation of Privilege | Banned user reaching a mutation | accept | `checkBanStatus()` kept exactly where it is (DEC-24); REFAC-11 in Phase 5 owns enforcement |
| T-04-05-05 | Repudiation | Loss of the auth-error warning logs on 401 (DEC-29) | accept | Wire bytes identical; recorded in the commit body and the decision record; auth-failure logging is Phase 6's structured logging |
| T-04-05-06 | Denial of Service | Unbounded row loads for RSVP counts | mitigate | Replaced by two server-side COUNTs (F-079) |
