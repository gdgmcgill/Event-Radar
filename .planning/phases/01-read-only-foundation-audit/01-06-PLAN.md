    Create `.planning/audit/tools/sql-readonly.mjs` as an ESM zero-dependency module using global fetch. It reads the project reference and the access token from the environment and exits 2 with a message naming only the missing variable NAMES when either is absent. It exports a query function that posts to the Supabase Management API database query endpoint for the configured project with a JSON body carrying the SQL, optional parameters, and a read-only flag set true — the read-only enforcement is server-side, which makes a write impossible rather than merely discouraged. Wrap the request in an abort-controller timeout and a bounded retry, following the timeout-and-retry structure used by `scripts/fix-instagram-images.ts`. Deviate from that analog in two ways that matter here: the credentials are the project reference and the personal access token, never the service-role key, because the service-role key is the RLS-bypassing credential this phase is auditing and it enforces nothing; and the terminal error handler must never print a caught error object whose message could embed a token or a connection string — print the HTTP status and a scrubbed body only.

    Create `.planning/audit/tools/sql-readonly-pg.mjs` as the fallback transport for the case where no access token is available. It loads the `pg` client from an out-of-repo module path supplied through `NODE_PATH`, connects with a connection string read from the environment, and issues a read-only transaction statement before any other statement. Document in its header that the install must target a scratch prefix outside the repository so `package.json` and `package-lock.json` stay untouched, and that the connection string is passed by environment variable only — never as a CLI argument that would land in shell history or in a captured log. Neither script may ever enable shell command tracing.

    Using the transport, capture the full production column census for the public schema — table name, column name, data type, nullability, and default, ordered by table and ordinal position — writing the raw rows to `.planning/audit/schema/information-schema-columns.json`. This file is both AUDIT-19's evidence and plan 01-08's drift-table input.

State which date and time columns exist on the production events table with their data types and nullability; state whether the older date and time column pair still exists in production; and give one of two verdicts with its consequence. If the older pair is absent, the concern is resolved in the database as well as in code — record the negative finding, and record that three Jest fixtures and a comment in the tag-mapping module still reference the removed columns, which makes those fixtures stale. If the older pair is still present but unreferenced by any handler, record a dead-column finding scoped to the Stage 3 event-read-path slice. Either way, name the authoritative columns explicitly, cite `information-schema-columns.json` by path, and state that the types file was treated as the artifact under suspicion rather than as evidence.
