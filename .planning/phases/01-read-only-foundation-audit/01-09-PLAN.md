Deliver the row-level-security slice end-to-end: the live policy capture, the enablement census, the four flag classes reviewed, a pivot generator, and the coverage grid that Stage 4's pgTAP matrix transcribes directly.

Purpose: An application that routes thirty-two tables through a backend-as-a-service is primarily secured by row-level security.     Emit one row per table and command pair, covering the four data-manipulation commands for every table in the enablement census, and one column per role. The role column set is the union of every role appearing in the capture, with the anonymous and signed-in roles always present as columns even when no policy names them, because their absence is precisely the interesting case.

    Each cell takes exactly one of three values: allow when a permissive policy grants the role that command on that table; deny when row security is enabled and no policy grants it; none when row security is disabled on the table so no policy applies and access is ungoverned. Distinguish deny from none carefully — they look similar in a grid and mean opposite things, and the whole value of the grid is that distinction. Render a table whose row security is disabled as none across its entire row.

    Add two trailing columns per row: a policy-count column and a notes column carrying the names of the policies that produced an allow, so a reader can trace a cell back to the raw capture.

    Run the pivot. The emitted row count must equal the number of distinct tables times four, and the validator enforces both that and the three-value cell constraint. Where the count disagrees, the pivot is dropping a table rather than the database being unusual.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| anonymous key → table data | Row-level security is the only control on this boundary for direct client reads |
| one tenant's rows → another tenant | A policy without a role clause or with an unconditional expression dissolves this boundary |
| captured policy expressions → git history | Policy expressions can embed literal identifiers or hard-coded values |
