## The credential checkpoint — what the operator answered

Task 1 was a `checkpoint:human-action` gate. It halted a previous executor because nothing it asked for was on disk. The resolution, recorded verbatim because the plan's action step requires it:

| Question | Operator's answer |
|---|---|
| Which credential path — access token or database password? | **Neither.** The Supabase **MCP server** (Management API) was authenticated in the orchestrator session instead. No `SUPABASE_ACCESS_TOKEN`, no `PROD_PROJECT_REF`, no `SUPABASE_DB_PASSWORD`, no `PROD_DB_URL` ever entered a shell environment on this machine. |
| Is the container daemon running? | **Yes** — OrbStack, server `29.4.0`. The daemon was never the blocker. |
| Does a staging project exist? | **"Not now."** A scheduling answer, not a denial. Separately, the MCP token sees exactly one project (`universe-events`); no staging project is visible under this account. |

Two consequences follow, and both are recorded rather than smoothed over:

1. Executor agents cannot call MCP tools. The orchestrator therefore dispatched a SELECT-only capture agent that ran 20 catalog queries and wrote `.planning/audit/raw/prod/`. This executor consumed those envelopes; it opened no connection of its own.
2. `supabase db dump` needs a connection string, and none exists. The container daemon being up does not help — Docker was never the missing piece.

## Decisions Made

1. **Record the transport that was actually used, prominently.** `prod.schema.sql`'s header, `events-date-columns.md`'s method section, and `redaction/01-06.md` all state that the capture ran over MCP and that `sql-readonly.mjs` was built but not exercised against production. A reviewer who assumed the plan's transport was used would draw a wrong conclusion about what enforced read-only.
2. **Treat the types file as the artifact under suspicion.** `src/lib/supabase/types.ts` was never consulted to derive the AUDIT-19 answer — only compared against the census afterwards, as a drift measurement. It agreed (25 properties, 25 columns, identical sets), but the ordering is what makes the verdict defensible.
3. **Withhold AUDIT-01 rather than claim it.** One environment of three, and that one by reconstruction. Marking it complete would put a false green in the traceability table at exactly the point where Stage 3 needs to know the schema story is incomplete.
4. **Leave `validate.mjs --check schema-snapshots` failing.** Its two failures name `staging.schema.sql` and `local.schema.sql`. That is the gate doing its job.
5. **Make the snapshot regenerable.** A 117 KB hand-assembled file is unreviewable and unmaintainable. `gen-prod-schema.mjs` produces it deterministically (verified byte-identical across two runs) so a re-capture yields a reviewable diff rather than a reshuffle.

## Findings produced

### Finding 1 — the migrations do not replay from zero (blocking, Stage 3 REFAC-01)

`supabase db reset` against the purely local containerised database aborts at **the 12th of 44 migrations**. Transcript: `.planning/audit/schema/local-reset.txt`.

- `008b_add_is_admin_to_users.sql` is **silently skipped** — its version does not parse from the filename's leading digits.
- `011_event_images_bucket.sql` and `011_rls_audit.sql` both derive version `011`; the second violates the primary key of `supabase_migrations.schema_migrations` and aborts the replay.
- Three further collisions (`008`, `20260305000002`, `20260306`) would abort subsequent attempts even if `011` were resolved.

This is not "input not supplied" — Docker was up and every migration file is present and tracked. The repository's own migration history is the blocker.

### Finding 2 — 45 applied migrations on production, 44 files in the repository

`raw/prod/migrations-applied.json` reports 45 applied versions; `supabase/migrations/*.sql` is 44 files. The counts do not agree, and the direction matters: production has applied something the repository does not contain, or has recorded a version the repository names differently. Plan 01-08 (AUDIT-02) owns the reconciliation; this plan records the discrepancy in `prod.schema.sql`'s migrations section and hands over the raw list.

### Finding 3 — five stale references to a schema that does not exist

Detailed with line numbers in `schema/events-date-columns.md`. In brief: `src/hooks/useEvents.test.ts:17-18` (a fixture assigning `event_date`/`event_time` to a typed `Event` that declares neither — an excess-property error invisible because `*.test.ts` is excluded from `tsconfig.json`, in a file whose tests are all skipped because `@testing-library/react` is not installed); `src/__tests__/api/clubs/analytics.test.ts:166-168` and `src/__tests__/api/events/analytics.test.ts:95,112,140` (fixtures supplying `event_date` to routes that select `start_date`, leaving `start_date` undefined and the tests passing only because their assertions look elsewhere); `src/lib/tagMapping.ts:98` and `supabase/functions/events-webhook/index.ts:99` (comments — the second also wrongly asserts that `club_id` and `status` are absent from `events`, which this census disproves).

### Finding 4 — three cron jobs, all pure SQL, none calling an endpoint

`raw/prod/cron-job.json`: `send-event-reminders` (`*/15 * * * *`), `compute-user-scores` (`0 */6 * * *`), `send-feedback-requests` (`*/30 * * * *`) — all active, all invoking a `public.` function directly. **No cron job issues an HTTP request**, so no production schedule invokes an application cron handler. That bears directly on the phase question "are the cron handlers ever invoked"; plan 01-10 owns the conclusion, and `raw/prod/cron-job-run-details.json` holds the last 100 run outcomes.

### Observation — RLS is enabled on all 30 public tables

From `raw/prod/tables.json`. Enablement is necessary, not sufficient: 101 policies and 143 table grants still need reconciling, and a table with RLS on and a `USING (true)` policy is open. Plan 01-09 owns that.

### Planned-artifact deviations (not rule-driven — these are checkpoint outcomes)

**A. The transport that captured production is not the transport this plan built.**
The plan specified `tools/sql-readonly.mjs`, whose Management API request body carries a server-enforced `read_only: true` flag. Production was instead read through the **Supabase MCP server**. From `raw/prod/transport-identity.json`:

| | |
|---|---|
| role | `postgres` |
| server_version | `17.6` |
| `transaction_read_only` | **`off`** |
| captures / failures / redactions | 20 / 0 / 0 |

**The MCP transport does not enforce read-only server-side.** The safeguard actually in force was **SELECT-only discipline**: every one of the 20 statements is a SELECT, each is recorded verbatim in its envelope's `query` field, all 20 succeeded, and no DDL or DML was issued. That claim is checkable — it is why the envelopes are committed. Both `sql-readonly.mjs` and `sql-readonly-pg.mjs` are retained unchanged as the documented path for a later credentialed pass; their acceptance criteria all pass (`read_only` present ×4, service-role references 0, `READ ONLY` in the fallback ×2).

**B. `prod.schema.sql` is catalog-derived, not a `pg_dump`.**
`supabase db dump` needs a connection string and none exists. Rather than leave AUDIT-01's production leg empty, the snapshot was reconstructed from the catalog captures and labelled as such in its first line. The exact command that produces the canonical dump — `supabase db dump --db-url "$PROD_DB_URL" --schema public,storage -f …` — is recorded in the header, in both stubs, and in the ledger.

**C. AUDIT-01 is withheld; only AUDIT-19 was marked complete.**
The plan's frontmatter claims both. One of three environments was captured, by reconstruction. `REQUIREMENTS.md` now carries the reason inline on the AUDIT-01 entry and in its traceability row, and a blocker is recorded in `STATE.md`.
