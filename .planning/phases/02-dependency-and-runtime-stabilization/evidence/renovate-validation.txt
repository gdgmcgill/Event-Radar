# ===========================================================================
# RULE ORDER — CHANGED FROM 02-RESEARCH.md § Code Examples 9, AND WHY
# ===========================================================================
#
# The research config lists the React-major rule FIFTH and the blanket
# "majors are never auto-merged" rule SIXTH. Here they are swapped: blanket fifth,
# React sixth. The rules are now ordered general -> specific.
#
# FUNCTIONALLY the two orderings are equivalent. Renovate applies packageRules in order
# and later matches override earlier ones, so a React major ends up `enabled: false`
# either way — in the research order it is disabled and then has automerge:false applied
# to an already-disabled update; in this order it has automerge:false applied and is then
# disabled outright.
#
# IT WAS CHANGED FOR A READER, NOT FOR RENOVATE. Both rules match exactly
# `"matchUpdateTypes": ["major"]`. In the research order, the FIRST rule matching that
# shape is the React-specific one, which carries `enabled: false` and no `automerge` key
# at all. Anything scanning the file for "the rule that stops majors auto-merging" —
# including 02-10-PLAN.md task 3's own verifier — finds the React rule, sees no
# `automerge: false` on it, and concludes the blanket protection is missing. It is not
# missing; it is shadowed. Putting the general rule first makes the file say what it
# means on a linear read, which is the whole reason every rule here carries a description.
#
# The reordered file was re-validated in both modes; both still exit 0. The output shown
# above is from the final, reordered file.

# THE ORDERING PROPERTY, which is the actual safety mechanism:
#
# Patch auto-merge merges when the required status checks pass. Before batch 0 of this
# phase those checks were lint + type-check + build, WITH NO TEST STEP AT ALL (F-065).
# This rule landing before batch 0 would have been a machine merging untested code into
# main every Monday morning. It lands in batch 6 because batch 0 added `npm test` to CI
# and batch 6a added the production vulnerability gate. The rule is not safe because it
# is restricted to patches; it is safe because of what "CI is green" now means.
#
# THE REACT RULE IS `enabled: false`, NOT `automerge: false`, AND THAT IS THE POINT:
#
# React 19 is deferred by project constraint and react/react-dom are phase-locked at
# ^18.3.0. `automerge: false` would still open a React 19 PR every week for a human to
# close. A bot that repeatedly proposes something the project has already decided against
# trains the team to close bot PRs unread — and the next unread bot PR is a security fix.
# So the PR is never opened. Threat T-02-10-02.
#
# SECURITY FIXES ARE EXEMPT FROM THE COOLING-OFF PERIOD:
#
# vulnerabilityAlerts.minimumReleaseAge = null deliberately overrides the global 3 days.
# The cooling-off exists to let a compromised publish be caught before it is merged; that
# reasoning does not apply to a fix for a vulnerability already public and already in the
# tree, where waiting three days is pure exposure.
