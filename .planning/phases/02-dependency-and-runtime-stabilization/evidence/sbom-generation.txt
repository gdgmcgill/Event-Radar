# WHY IT MATTERS. vercel.json deploys this application to region iad1 — Linux x64.
# Those three packages are precisely the native binaries that RUN IN PRODUCTION. An SBOM
# generated on a developer's Mac and committed would have omitted the binaries that
# actually ship, which is the single most expensive way for a bill of materials to be
# wrong: a consumer scanning it for a native-binary advisory would find nothing.
#
# It also breaks this plan's own must-have. `must_haves.truths` requires "The SBOM is
# byte-stable across regenerations, so a diff on it means the tree actually changed."
# In installed-tree mode that is FALSE across machines — regenerating on ubuntu-latest
# with an unchanged lockfile produces a different document, so the CI freshness check
# the plan names as the point of the exercise could never pass. With --package-lock-only
# the document depends only on package.json + package-lock.json, both committed, so the
# guarantee holds on any host.
#
# It is also what the plan asks for in words: 02-10-PLAN.md `key_links` says the SBOM is
# "generated from the final lockfile", and this flag is what makes that literally true.
#
# WHAT IT COSTS. Lockfile mode cannot see each package's own package.json on disk, so
# two human-readable fields are lost. Measured, not guessed:
#
#   field              installed-tree      lockfile mode
#   components               288                320

#   with licenses            286/288            318/320
#   with externalReferences  288/288            320/320
#   with description         258/288              0/320
#   dependency graph edges   319                351
#
# purls, licences, external references and the dependency graph — everything an SBOM is
# consumed for — are preserved or improved. Only `description` and `author`, which no
# scanner reads, are lost. The trade was taken.

# ===========================================================================
# THE RULE FOR WHOEVER TOUCHES THE LOCKFILE NEXT
#
#   >>> sbom.cyclonedx.json IS GENERATED. NEVER HAND-EDIT IT. <<<
#   >>> REGENERATE IT IN THE SAME COMMIT AS ANY package-lock.json CHANGE. <<<
#
# The handling rule is copied from .planning/audit/quality/npm-audit.prod.json — a
# committed, generated, never-hand-edited JSON — per 02-PATTERNS.md § No Analog Found.
# There is no SBOM precedent in this repository; this is the first one.
#
# A lockfile change without a matching SBOM regeneration produces the one failure mode
# that makes an SBOM worse than having none: a document that is trusted because it is
# committed and wrong because it is stale. If a dependency moves, run:
#
#   npx --yes @cyclonedx/cyclonedx-npm@6.0.1 --omit dev --package-lock-only \
#     --spec-version 1.6 --output-format JSON --output-file sbom.cyclonedx.json \
#     --output-reproducible --validate --mc-type application package.json
#
# and commit the result alongside the lockfile. Because the output is reproducible, a
# regeneration with no lockfile change produces no diff at all — so running it
# unnecessarily costs nothing, and NOT running it is the only way to get this wrong.
