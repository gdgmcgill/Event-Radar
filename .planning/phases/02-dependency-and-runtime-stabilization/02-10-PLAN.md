Do not install it — adding an SBOM generator to the dependency tree it is measuring is self-defeating, and the same reasoning already governs the codemod and the browserslist updater in earlier batches.

Five things about the invocation matter:

Omit development dependencies, so the document describes the production tree the vulnerability policy also scopes itself to.

Pin the CycloneDX specification version explicitly rather than accepting the tool's default, so a future tool upgrade does not silently change the document's shape.

Emit JSON, to the repository root, as `sbom.cyclonedx.json`.

Use the reproducible-output flag. This is **not optional for a committed SBOM**: without it the document's serial number and timestamps change on every run, so the file shows a diff every time it is regenerated and stops being a meaningful artifact — you could never tell a real dependency change from a re-run.

Use the validation flag, so the command fails if the document does not satisfy the CycloneDX schema. An SBOM that validates against nothing is one of the easy-to-write, expensive-to-be-wrong-about artifacts.

Set the main component type to application.

Capture the full command and its output, including the exit code, into `evidence/sbom-generation.txt` with a provenance block.

Then prove reproducibility rather than assuming it: regenerate to stdout with the identical flags and diff against the committed file. They must be byte-identical. Record that check and its result in the same evidence file — that is what makes the document trustworthy as a committed artifact and it is the basis of any future CI freshness check.

The SBOM is generated, never hand-edited. Regenerate it in the same commit as any future lockfile change; state that rule inside `evidence/sbom-generation.txt` so the next person reads it.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| update bot → default branch | Auto-merge lets a machine land dependency changes without a human reading them |
| SBOM → downstream consumers | A committed bill of materials is treated as an accurate description of what ships |
| build output → recorded metrics | Bundle figures are quoted in the exit-gate note |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-10-01 | Tampering | Compromised package auto-merged by the bot | mitigate | A three-day minimum release age as a cooling-off period, auto-merge restricted to patch-like update types only, auto-merge conditional on CI passing — which now includes the test suite and the production audit gate — and every group containing a high-blast-radius package explicitly excluded from auto-merge |
| T-02-10-02 | Tampering | React pulled to 19 by a bot pull request against a project constraint | mitigate | Major updates for React, React DOM, and their type packages are **disabled**, not merely un-auto-merged, so the pull request is never opened. Separately, no major auto-merges at all |
| T-02-10-03 | Repudiation | An SBOM that drifts from the lockfile and is trusted anyway | mitigate | Generated from the final lockfile with the reproducible-output flag, byte-stability proven by a regenerate-and-diff check recorded in the evidence, schema validation enforced by the generator, and a written regenerate-with-every-lockfile-change rule |
| T-02-10-04 | Spoofing | Malicious SBOM generator or configuration validator via one-shot execution | mitigate | Both run at pinned versions.
