<objective>
Batch 6a: turn the vulnerability policy into a gate that actually runs, and close the register behind it.

The CI production audit step is added **last**, on purpose. It exits 1 on the pre-remediation tree, so adding it in batch 0 would have made every pull request red for five batches and taught the team to merge past a red check. A gate present in config but never green is a worse outcome than no gate — it is the exact shape of F-065, which is how this repository ended up with a CI pipeline that never ran its tests.

Purpose: STAB-14 asks for the step; STAB-17's exit gate asks for something harder — no unexplained Critical, and no reachable High without a dated, owner-signed exception. This plan measures the final census, fills or empties the exception register against it, adds the step, and records a green run.
Output: the CI step, the final census, the filled exception register, and the green run record.

</objective>

**Criticals.** The count must be zero. A Critical may not be risk-accepted — the inherited SLA is unambiguous, a Critical is either fixed or the program stops. If one survives, stop this plan and escalate; do not add the CI step over the top of it and do not write an exception for it.

Either it is fixed — in which case fix it in a properly reconciled, reviewed commit following the batch protocol, not with a forced remediation command — or it gets a row in the exception register. A register row is only complete with all four attributes: a named human as `owner` (not a team, not a role), an ISO `date`, an `expiry` no more than 90 days after that date, and a `rationale` that is a **reachability argument** — why the defect cannot be reached from a production entry point, or what compensating control bounds it. "Low priority", "no time", and "unlikely" are explicitly not rationales. An expired acceptance reverts to Open automatically.

If the High count is zero, say so in the register section explicitly — an empty table with a sentence stating that no exception was required is a stronger artifact than a table a reader cannot tell was left unfilled.

Then update the policy's named-open-items table with each item's **actual** post-remediation status, replacing the expected status written in batch 0. Pay attention to two of them specifically. The build-only pattern-matching advisory needed *both* an in-range update and the Tailwind plugin's move out of production dependencies — verify both, not one, and record both. And the cache-poisoning row is closed by version while its precondition remains live on this deployment: keep the F-025 citation and the pointer to REFAC-19 in Phase 6 intact, and do not soften it now that the count looks good.

Record the Moderate and Low counts too. They are tracked, not blocking, and the completion note quotes them.

## Trust Boundaries

| Boundary | Description |

| pull request → merge | The audit gate is the mechanical control standing between a vulnerable dependency and the default branch |
| exception register → the exit gate | A register row is the only documented bypass of that control |
| CI logs → evidence | Workflow logs are read and quoted into committed files |
