# D-16, stated plainly: the migration role is `postgres`; it holds no CREATE on the storage
# schema, so a dumped `CREATE TYPE "storage"."buckettype"` cannot be replayed. This is
# equally true in production — the storage schema is owned and created by the storage
# SERVICE in every environment, from the same image. Probes that established it, run
# directly against the local database as `postgres`:
#
#   has_schema_privilege('postgres','storage','CREATE')          -> f
#   pg_tables.tableowner for storage.objects                     -> supabase_storage_admin
#   pg_roles.rolsuper for postgres                               -> f
#   pg_has_role('postgres','supabase_storage_admin','MEMBER')    -> f
#   CREATE POLICY ... ON storage.objects                         -> CREATE POLICY   (PERMITTED)
#   CREATE TYPE storage.__probe_t AS ENUM ('a')                  -> permission denied for schema storage
#   ALTER TABLE storage.objects ENABLE ROW LEVEL SECURITY        -> must be owner of table objects
#   pg_class.relrowsecurity for storage.objects, pre-migration   -> t  (the service already enabled it)
#   count(information_schema.tables where table_schema='storage')-> 10 (present before any migration)
#
# So the privilege boundary falls exactly where the ownership boundary does: storage
# POLICIES are application-owned and creatable; storage STRUCTURE is service-owned and is
# not this repository's to declare. The baseline was rebuilt to carry `public` in full plus
# the 15 storage.objects policies, and nothing else from the storage schema.
