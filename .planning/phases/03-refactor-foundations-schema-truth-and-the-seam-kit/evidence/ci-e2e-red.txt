=== 3. THE MECHANISM, PINNED TO LINES ===

--- .github/workflows/ci.yml:9-11 — a WORKFLOW-LEVEL env block, inherited by EVERY job ---
env:
  NEXT_PUBLIC_SUPABASE_URL: "https://placeholder.supabase.co"
  NEXT_PUBLIC_SUPABASE_ANON_KEY: "placeholder-key"

--- e2e/env.ts:29-32 — the placeholder is truthy, so it wins ---
  const fromEnv = {
    url: process.env.SUPABASE_URL ?? process.env.NEXT_PUBLIC_SUPABASE_URL,
    anonKey: process.env.SUPABASE_ANON_KEY ?? process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY,
    serviceRoleKey: process.env.SUPABASE_SERVICE_ROLE_KEY,

--- e2e/env.ts:61-65 — and `??` only falls through on null/undefined ---
  cached = {
    url: fromEnv.url ?? read("API_URL"),
    anonKey: fromEnv.anonKey ?? read("ANON_KEY"),
    serviceRoleKey: fromEnv.serviceRoleKey ?? read("SERVICE_ROLE_KEY"),
  };

# On the runner NEXT_PUBLIC_SUPABASE_URL is 'https://placeholder.supabase.co',
# so fromEnv.url is TRUTHY and read("API_URL") — the real local stack URL from
# `supabase status -o env` — is never consulted. playwright.config.ts:89 then
# hands the placeholder to assertSeedTargetAllowed, which refuses it.
#
# THE GUARD IS CORRECT. It is doing exactly what scripts/seed/guard.ts was built
# to do: refuse a target that is neither local nor an acknowledged staging project.
# The defect is the job's environment, not the control that caught it.
#
# It passes locally because a developer's shell does NOT export
# NEXT_PUBLIC_SUPABASE_URL — .env.local is a file, not an export — so fromEnv.url
# is undefined and the API_URL branch is taken. That asymmetry is the whole bug.

=== 6. THE FIX, WORKED OUT — and why this plan did not apply it ===

# Two layers could own it, and the choice is a real decision rather than a typo fix.

# OPTION A — the workflow. Give the e2e job the local stack's real values after
#   `supabase start`, so nothing downstream has to guess:
#
#     - name: Export the local stack credentials to the job environment
#       run: |
#         supabase status -o env | sed -n \
#           -e 's/^API_URL="\?\(.*[^"]\)"\?$/NEXT_PUBLIC_SUPABASE_URL=\1/p' \
#           -e 's/^ANON_KEY="\?\(.*[^"]\)"\?$/NEXT_PUBLIC_SUPABASE_ANON_KEY=\1/p' \
#           -e 's/^SERVICE_ROLE_KEY="\?\(.*[^"]\)"\?$/SUPABASE_SERVICE_ROLE_KEY=\1/p' \
#           >> "$GITHUB_ENV"
#
#   Placed after 'Start local Supabase stack'. It overrides the inherited
#   placeholder with the truth, and the guard then allows 127.0.0.1 as designed.
#   NOTE: this writes a service-role key into $GITHUB_ENV. It is the LOCAL
#   stack's throwaway key, not production's — but it will appear in the job's
#   environment, so whoever takes this should confirm that is acceptable or use
#   Option B instead.

# OPTION B — e2e/env.ts. Stop letting an ambient variable outrank the running
#   stack. Prefer `supabase status -o env` and treat the process environment as
#   the fallback, not the override — the inverse of the current precedence at
#   e2e/env.ts:29-32 and :61-65. Strictly safer, because no credential crosses a
#   step boundary, and it makes the harness impossible to aim at a non-local
#   target by an inherited variable. It is an application-adjacent source change.

# RECOMMENDED: Option B, with Option A's export step as a belt-and-braces addition
#   only if the build step also needs the real values.

# WHY NOT HERE. Neither .github/workflows/ci.yml nor e2e/env.ts is in plan 03-08's
#   files_modified, and this plan's own prohibition is that it 'changes no source,
#   no migration and no test — its outputs are records'. More to the point: a fix
#   to a CI job cannot be VERIFIED from this laptop. It needs a push and an
#   observed run, and shipping an unverified fix inside the note whose entire
#   standard is 'every claim cites a committed artifact' would be the one kind of
#   change this document must not contain. The diagnosis is complete and
#   reproducible; applying it is one commit and one observed run.
