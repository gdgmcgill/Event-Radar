<objective>
Wave 3: land the two schema fixes the audit identified, each with a database test that would fail if the fix were removed — and prove that claim by removing it.

Purpose: REFAC-02 and REFAC-03 are small in SQL and large in discipline. The SQL is nine foreign-key indexes, one composite index, one orphaned table drop, a handful of policies the audit named as gaps, and one cron schedule. The discipline is that each of those must carry a test that actually bites, in a tier where the standard way of writing tests does not bite at all.

That is not a general worry, it is this program's own finding one tier down. `02-REVIEW.md` WR-04 found a Phase 2 characterization suite whose assertions could not fail when the preserved behaviour was removed. The pgTAP equivalent is worse, because RLS denial has two distinct shapes — a raised error and a silent zero-row filter — and the obvious assertion only notices one of them. A liveness assertion on an insert passes when the insert matched zero rows, so a broken policy reads as a working one.

So this plan writes the tests in the shapes that can fail, and then mechanically proves each one fails: comment the policy out, require red, restore, require green. That harness is a deliverable, not a ritual.

Output: two new post-baseline migrations, a pgTAP setup file with in-repo impersonation helpers, three test files, an automated mutation-check harness, an idempotence proof across two resets, a still-clean diff with every deliberate addition named, and a note recording what was deliberately not fixed.

**No CONTEXT.md exists for this phase.** The binding constraint here comes from 03-RESEARCH.md § Phase Constraints: this plan fixes only the audit-identified gaps and missing FK indexes REFAC-02 names, and explicitly does **not** attempt the full 41-versus-24 policy divergence, which is Phase 5's work.
</objective>

Create the second new migration, for REFAC-03. Ensure the cron extension exists, then make the schedule idempotent: guard on the job catalog and unschedule by name only if a job with that name is already present, then schedule it. Guarding on the catalog rather than swallowing an exception matters because the unschedule call raises when the job is absent, and a migration that swallows exceptions hides the case where it did nothing. Create `020-rls-policy-gaps.test.sql` with an allow/deny pair for every policy task 1 created. Follow the denial table exactly. A missing grant and a with-check violation both raise, so assert the raise. Never prove an allowed write with a liveness assertion: it passes when the write matched zero rows. Use a returning clause and assert the returned value. The suite must be transactional and roll back, so it leaves no rows behind and can run against a freshly reset database any number of times.

Create `030-cron-schedule.test.sql` with two assertions: that the job's schedule expression equals production's, and that exactly one job with that name exists. The second is the idempotence assertion and it is what makes a double reset meaningful.
