<objective>
Wave 5: build the deterministic seed and the persona harness — the net every later slice falls into when it refactors a workflow.

Purpose: Phases 4, 5 and 6 rewrite the authorization ring, the event read path and the asynchronous edge. The program's core value is that no workflow which worked before stops working. That promise needs two things which do not exist today: data whose every row is predictable, and a way to be six different users without a real Google account.

Both have a specific technical answer this research verified rather than assumed. The admin user-creation API accepts an explicit id, which means fixed UUIDs without hand-writing into the auth schema — no password hashing, no identity row to guess, no drift risk against a schema the vendor owns. And persona sessions are produced by handing the library's own cookie serializer a sign-in and capturing what it emits, which means no cookie format is ever guessed and no application change is needed.

Two honest limits belong in the plan rather than in a later surprise. There is no staging environment — the Phase 1 capture says so plainly — so REFAC-07's "local and staging" is discharged as a guarded, unit-tested staging branch with no project to load into, recorded as a partial. And personas authenticated by cookie injection never traverse the auth callback, so McGill enforcement and admin auto-assignment are covered by plan 03-02's unit characterization and not by this harness.

Output: five seed modules with a fail-closed target guard and its refusal tests, a coverage assertion at the database tier, a determinism proof, one exact-pinned package, a Playwright config, ten storage states, six happy-path specs, a cookie-equivalence cross-check, a CI job, and a note recording both limits.

**No CONTEXT.md exists for this phase.** The binding decisions here are D-03 (exactly one new package name, pinned), D-06 (the loader hard-refuses any non-local target and refuses anything matching the production ref; the staging clause is a stated partial, not a hidden one) and D-07 (persona sign-in uses the admin creation API for fixed ids plus the library's cookie serializer with browser-context injection — no application change, no real OAuth).
</objective>

Sign in once per persona per run and never re-authenticate inside a spec. The local stack rate-limits sign-ins per window and a re-authenticating spec suite trips it in a way that reads like an outage.

Add no test-only sign-in route and change no application file. A new route would be a behaviour change and an attack surface, in the phase whose core value is behaviour preservation.
