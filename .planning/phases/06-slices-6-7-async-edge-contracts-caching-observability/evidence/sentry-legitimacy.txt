  (section 4).

- A7, the transitive @sentry/cli (section 8): 10.75.3 depends on @sentry/bundler-plugin-core ^5.3.0 and
  @sentry/webpack-plugin ^5.3.0. The webpack plugin's newest 5.x is 5.4.0 (2026-07-10), which depends on
  @sentry/bundler-plugins ^10.64.0, and @sentry/bundler-plugins@10.75.3 depends on @sentry/cli ^2.58.6;
  bundler-plugin-core 5.x depends on @sentry/cli ^2.58.5. Both resolve to @sentry/cli@2.58.6, whose
  package.json runs `postinstall: node ./scripts/install.js`. That script fetches the platform binary when
  the matching optional package (@sentry/cli-darwin, -linux-x64, … all 2.58.6) is absent, so it is a
  network-capable install script. The binary is used only for source-map upload, which 06-16 disables
  without SENTRY_AUTH_TOKEN. Installation therefore runs with SENTRYCLI_SKIP_DOWNLOAD=1, and CI sets the
  same variable at workflow level (DEC-61). 06-16 records which @sentry/cli and platform package the
  lockfile resolves.
- The unscoped `sentry` package (research's Package Legitimacy Audit, row 4) is a dependency of
  @sentry/bundler-plugins 11.0.0 only (section 8); the 10.75.3 chain does not pull it in.
- Seam: `package-legitimacy check` answers verdict SUS with the single reason `too-new`. The seam
  evaluates the LATEST version (its publishedAt is 11.0.0's, 12:38Z), not the pin; 10.75.3 is also two
  days old. That is release cadence, not identity. DEC-61 resolves it by rule (exact pin, integrity
  comparison at install, SENTRYCLI_SKIP_DOWNLOAD=1, owner countersignature carried to the completion note
  as a human-check).
