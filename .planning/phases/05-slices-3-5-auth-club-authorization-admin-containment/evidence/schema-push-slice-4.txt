Why step 10 ran after the commit, not before it: the mutation check restores migrations with
`git checkout --` and refuses to start while a listed migration has uncommitted changes (its
"FATAL: … has uncommitted changes" guard). The new migration was untracked until 5d9c22e, so the
check had to run on the committed file. Its result is exit 0, so no follow-up commit was needed.

Why step 10b exists: the harness removes a policy by commenting out its CREATE. Because the new
file DROPs the baseline policy first, removal leaves NO events INSERT policy, which denies
everything. That turns the allow rows red (7, 8, 9, 12, 13, 14) but cannot turn a deny row red.
The regression F-008 describes is the opposite, the policy put back to WITH CHECK (true), so 10b
applies exactly that to the running local database (no file edited) and shows the five deny rows go
red. Together, 10 and 10b show that every events-INSERT row in 060 fails when its half of the policy
is wrong.
