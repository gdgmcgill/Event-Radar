## 2. What "404" means on /users/[id] (measured; a deviation from the plan's wording)

src/app/loading.tsx wraps every page in a Suspense boundary. The response therefore starts
streaming with HTTP 200 before the page component runs, and notFound() renders the not-found UI
into the stream with <meta name="robots" content="noindex"/>. This is Next's documented behaviour
(node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/loading.md, "Status Codes":
"When streaming, a 200 status code will be returned ... Because the response headers have already
been sent to the client, the status code of the response cannot be updated."). A profile id with
no users row has always answered this way.

Probe against the built app (next start on :3000, local stack), anonymous curl:
  missing status=200   (id 5eed0000-0000-4000-8000-00000000dead)
  public status=200
  private status=200   (onboarded_student set private with psql, then restored to public)
  == missing: name=0 email=0 noindex=2 pagenotfound=1
  == public:  name=2 email=0 noindex=0 pagenotfound=1
  == private: name=0 email=0 noindex=2 pagenotfound=1
  <title>: missing and private both "UNI-VERSE | McGill Campus Events"; public "Seed Onboarded Student | UNI-VERSE | UNI-VERSE"
("Page Not Found" is present in every response's RSC payload, so it is not a discriminator; the
noindex meta and the absent name are.)

So public-profile-privacy.spec.ts asserts the property a reader cares about: the anonymous
response for a private profile is the same not-found response a missing profile gets (same status,
same title, the noindex meta), and carries neither the owner's name nor their email. A hard HTTP
404 would need the check before streaming, i.e. in the proxy or by removing the root loading
boundary; neither is in this plan's scope. Candidate deferred item for 05-19.
