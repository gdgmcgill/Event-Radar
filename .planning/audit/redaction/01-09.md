**Result:** **no scrub was required.** Every pattern in `REDACTION.md`'s phase-gate sweep returned a

## 1. How credentials were handled

**No credential of any kind entered this machine's shell environment during this plan, and this plan
opened no network connection.**

Continuing the resolution recorded in `01-06-SUMMARY.md` and `redaction/01-06.md`: production was
read **once**, by the orchestrator, through the authenticated **Supabase MCP server** (Management
API), SELECT-only, as role `postgres`. Those reads were committed as capture envelopes under
`.planning/audit/raw/prod/`. This plan consumed **only those committed envelopes from local disk**.

| | Planned path (01-09 PLAN.md Task 1) | Path actually used |
|---|---|---|
| Transport | `tools/sql-readonly.mjs` → Management API, per query | `raw/prod/*.json`, already on disk, read with `fs.readFileSync` |
| Credential material | `SUPABASE_ACCESS_TOKEN` or a `postgres://` URI | none — no credential was needed or present |
| Network connections opened by this plan | 4 | **0** |
| Could a credential reach an artifact? | yes, via an error object or a traced command | no — none existed in the environment |

Specifics, stated because they govern the next pass as much as this one:

- `SUPABASE_ACCESS_TOKEN`, `PROD_PROJECT_REF`, `STAGING_PROJECT_REF`, `SUPABASE_DB_PASSWORD`,
  `PROD_DB_URL` and `STAGING_DB_URL` were **unset for the duration of the plan**. No secret was
  passed as a command-line argument, because no command in this plan took one.
- **Shell command tracing: enabled once, recorded here rather than omitted.** `set -x` was switched
  on for a single Task 1 verification block — the five `node -e` one-liners that re-check the plan's
  acceptance criteria — and switched off again with `set +x` before the sweep ran. It is recorded
  because `tools/readonly-guard.sh` carries an explicit comment forbidding tracing in this phase, and
  a ledger that quietly drops an inconvenient fact is worthless. The exposure it creates is nil, and
  the reason is checkable rather than asserted: `set -x` echoes the *expanded command line*, and every
  command inside that block was a literal `node -e '…'` string containing a file path and no variable
  expansion at all. There was no credential in the environment to expand (see the paragraph above),
  the trace was written to the terminal and to no file, and no script written by this plan enables
  tracing. No command that touched a credential, a URL, or a header was ever traced — this plan runs
  no such command.
- `tools/pivot-rls-heatmap.mjs`, the one tool this plan adds, reads no environment variable at all —
  it has no `process.env` access of any kind, so it cannot leak one.
- **The audited credential is never the transport.** `tools/pivot-rls-heatmap.mjs` contains zero
  references to `createServiceClient`, `SUPABASE_SERVICE_ROLE_KEY`, or `@supabase/supabase-js`. The
  service-role key is the RLS-bypassing credential this plan exists to audit; using it to perform the
  audit would be circular, and — the point worth stating for AUDIT-05 specifically — **it enforces
  nothing**, so a capture taken through it would have shown a policy set that does not apply to it.
- **No package manager was invoked.** The one tool added uses Node built-ins only (`node:fs`,
  `node:path`). `package.json` and `package-lock.json` are byte-identical; asserted by
  `tools/readonly-guard.sh` check 2 after every task.
- **No write of any kind reached the database.** This plan issued no SQL.

**Every count is zero, on values and on definitions alike.** Unlike plans 01-06 and 01-08, this
plan's tool contains no scrub table of its own — `pivot-rls-heatmap.mjs` never prints an error body
because it never has one to print — so there is not even a pattern *definition* to itemise and
dismiss. The self-reference caveat in `REDACTION.md` applies to **this note only**, which names the
patterns and will therefore match them at the phase gate.

### The sweep was run under `bash`, with an array — deliberately

```bash
bash -c 'FILES=(.planning/audit/rls/pg_policies.json ... )
PATTERNS=( ... the eleven above ... )
for p in "${PATTERNS[@]}"; do
  for f in "${FILES[@]}"; do command grep -cE "$p" "$f"; done
done'
```

Plan 01-08 recorded a false-clean caused by running exactly this loop under `zsh`, where an unquoted
`$FILES` holding a space-separated path list does **not** word-split: the loop passes one long
non-existent path and prints `0` for every pattern. That failure mode is not hypothetical here, it is
the documented history of this phase's sweep. Two controls were applied:

1. The sweep ran under `bash -c` with a real array, never an unquoted variable holding a path list.
2. **A positive control was run alongside it.** The same loop was executed with the pattern
   `auth\.uid` — a string that must appear in `pg_policies.json` and in `rls-flags.json` — and it
   returned `65` and `49` respectively, with `0` for the two artifacts that carry no expression text.
   A zero count is only evidence if the command that produced it was capable of producing a non-zero
   one; that is what the positive control demonstrates.

## 4. Policy expressions, inspected specifically

The plan singles this out, correctly: a policy expression is arbitrary SQL and can embed a
hard-coded value that no schema-level sweep would think to look for. Every string literal in every
`qual` and `with_check` across all 101 captured policies was extracted and enumerated:

```bash
node -e "…extract /'[^']*'/g from qual and with_check across all 101 policies…"
```

**Ten distinct literals, in full:**

`'admin'`, `'appeal'`, `'approved'`, `'authenticated'`, `'banners'`, `'club'`, `'club-logos'`,
`'event'`, `'event-images'`, `'service_role'`

Classified: three Postgres role names (`authenticated`, `service_role`) and a `user_role` enum value
(`admin`); four application enum / discriminator values (`appeal`, `approved`, `club`, `event`); and
three storage bucket names (`banners`, `club-logos`, `event-images`). **None is a credential, a key,
a token, a URL, or a personal identifier.** Bucket names are public path components already visible
in any object URL the application renders, and are named in `supabase/migrations/011_event_images_bucket.sql`.

**No scrub was performed on any expression, because no expression carried a value requiring one.**
Had one, the substitution would be recorded here with the placeholder and the command, per
`REDACTION.md` § Standard placeholders.

## 5. Deliberate exclusions

"Excluded" means *never captured in the first place*, which is the only exclusion that is safe once
`commit_docs` is `true` and the artifact is in git history permanently.

| Excluded | From | Why |
|---|---|---|
| The `auth` schema | every artifact | `pg_policies` was scoped to `schemaname IN ('public','storage')` at capture time. An `auth` policy set can name `supabase_auth_admin` grants and carry GUC references; it is out of AUDIT-05's scope and would be in git permanently. |
| Row data | every artifact | AUDIT-05 is a question about policies, not about what they return. No policy was *evaluated* — none was tested by issuing a query as `anon` or `authenticated`, which would have required a session token. The heatmap's `allow`/`deny` cells are derived **statically** from the catalog, and `rls-review.md` says so where it matters. |
| The `cron` schema's two relations | `rls-enabled.json` and the heatmap | `raw/prod/tables.json` carries `cron.job` and `cron.job_run_details`. Both are excluded: AUDIT-05's scope is `public` and `storage`, `cron` is owned by AUDIT-11 in plan 01-10, and neither carries a policy. Recorded so the 38-vs-40 relation count is legible rather than read as a dropped table. |
| The production hostname and project reference | every artifact | Never needed. Production was not contacted by this plan; the committed envelopes already store the ref as `<PROD-PROJECT-REF>`. |
| Function **bodies** | every artifact | `raw/prod/functions.json` carries full `pg_get_functiondef` text and was read to check the two SECURITY DEFINER helpers that policies call (`is_admin()`, `is_club_owner()`). Their `search_path` settings are **described** in `rls-review.md`; no function body was copied into an artifact this plan writes. A function body is the classic carrier for an inline key. |
