# Redaction ledger — plan 01-08 (schema-drift slice)

**Plan:** 01-08 — migration history for three environments, shadow-database diffs, three-way drift table
**Date:** 2026-09-14
**Requirements touched:** AUDIT-02
**Result:** **no scrub was required.** Every pattern in `REDACTION.md`'s phase-gate sweep returned a
count of **zero** across the eight artifacts this plan produced, with one non-zero count that is a
pattern *definition* inside this plan's own generator, itemised and dismissed in § 3.

This note is the per-plan entry that `.planning/audit/REDACTION.md` says plan 01-13 concatenates into
the phase ledger. It is written because this plan **sits on a credential path** — its planned commands
(`supabase migration list --db-url`, `supabase db diff --project-ref`) take a connection string or an
access token — and a plan on a credential path that leaves no note here is a gate failure, not an
oversight. That the credential never materialised does not excuse the note; it is the note's content.

## 1. How credentials were handled

**No credential of any kind entered this machine's shell environment during this plan.** There was
therefore no value available to leak into an artifact. That is a stronger guarantee than scrubbing,
and it is the reason every count in § 3 is zero.

Concretely:

- `SUPABASE_ACCESS_TOKEN`, `PROD_PROJECT_REF`, `STAGING_PROJECT_REF`, `SUPABASE_DB_PASSWORD`,
  `PROD_DB_URL` and `STAGING_DB_URL` were all unset for the duration of the plan. Continuing plan
  01-06's resolution, production was read through the authenticated **Supabase MCP server**
  (Management API), whose OAuth grant is held by the agent runtime and lives outside the repository
  and outside the shell entirely.
- **No secret was passed as a command-line argument.** This is stated as practice and as fact. Every
  command recorded inside the artifacts this plan wrote uses the **environment variable** form —
  `supabase migration list --db-url "$PROD_DB_URL"`, `supabase db diff --project-ref
  "$STAGING_PROJECT_REF"` — so the literal is dereferenced by the shell at run time and never appears
  in an argument vector, in shell history, or in a captured log. The variable NAMES are the only
  credential-adjacent strings written to disk by this plan, which is exactly what
  `.planning/audit/BLOCKING-INPUTS.md` is for.
- **No shell command tracing.** `set -x` was not enabled in any command or script run by this plan,
  and the generator this plan added (`tools/gen-drift-table.mjs`) contains no tracing and no
  `process.env` read of any kind.
- **No `supabase link`.** Linking would have written project state — including the project reference —
  into `supabase/.temp/`, inside the directory under audit. The per-command `--project-ref` /
  `--db-url` forms recorded in the artifacts avoid that write by construction.
- **Errors are scrubbed before they are printed.** `tools/gen-drift-table.mjs` installs a terminal
  error handler that rewrites a JWT shape, an `sb_secret_`-prefixed key, and a password-bearing
  `postgres://` URI to placeholders before any error text reaches stderr, mirroring the table already
  present in `tools/sql-readonly.mjs`. A caught error object is never printed raw.
- **The audited credential is never the transport.** The generator reads only local files — the
  captured census, `supabase/migrations/`, and `src/lib/supabase/types.ts`. It opens no network
  connection, references neither `createServiceClient` nor `SUPABASE_SERVICE_ROLE_KEY`, and installs
  nothing.

### The single non-zero count, itemised and dismissed

Pattern 2 matches once, in `.planning/audit/tools/gen-drift-table.mjs`, inside the generator's own
`scrub()` function:

```js
.replace(/sb_secret_[A-Za-z0-9_-]+/g, "<REDACTED-SECRET-KEY>")
```

That is a **pattern definition, not a value** — the literal `sb_secret_` followed by a character
class, not followed by a key. `REDACTION.md` § Self-reference caveat already carves out `tools/` for
exactly this reason, alongside `REDACTION.md` itself. Verified by eye. No scrub performed.

Patterns 1 and 4 also appear as definitions in the same function but do **not** register as hits,
because in ERE the definition text `eyJ[A-Za-z0-9_-]{10,}` is read as *"eyJ followed by at least ten
characters from the class"* and the literal `[`, `]`, `{`, `,` that follow `eyJ` in the source are
not in that class. Pattern 2 is the only one of the seven whose definition is literal enough to
match itself. This is a property of the patterns, not a gap in the sweep.

### How the sweep was run, and a false-clean that was caught

```bash
bash -c 'FILES=(...eight paths...)
for p in <the seven patterns>; do
  for f in "${FILES[@]}"; do grep -cE "$p" "$f"; done
done'
```

**Run under `bash`, with an array — deliberately, not incidentally.** The interactive shell for this
phase is `zsh`, where an unquoted `$FILES` holding a space-separated path list does **not** word-split.
A naive `grep -cE "$p" $FILES` under `zsh` therefore passes one long non-existent path, matches
nothing, and prints `0` for every pattern. The first run of this sweep did exactly that and reported
a clean result for all seven patterns; the discrepancy was caught by spot-checking a single file
directly, which returned `1` where the loop had returned `0`. The counts in the table above are the
re-derived ones.

Recording this is the point of a redaction ledger. **A sweep that cannot fail is not a sweep**, and a
zero count is only evidence if the command that produced it was capable of producing a non-zero one.
Any later pass that re-runs these patterns under `zsh` must use an array or `git grep`, never an
unquoted variable holding a path list.

**No scrub was performed, because no count was non-zero on a value.** Pattern 7 is the shape-based stand-in for
`REDACTION.md` sweep row 6: that row says to read `$PROD_PROJECT_REF` and `$STAGING_PROJECT_REF` from
the environment at sweep time, and both are unset here (§ 1), so the sweep was run against the
*shape* instead. A shape sweep is strictly broader than a literal sweep — it would flag any 20-char
lowercase token, project ref or not — so a zero count on the shape proves a zero count on the
literals without ever needing the literals.

**Self-reference caveat.** This file names the patterns, so a naive sweep of the whole of
`.planning/audit/` will count hits inside `redaction/01-08.md` itself. Those are pattern definitions,
not values, and `REDACTION.md` already carves out that exclusion for itself and for `tools/`. The
counts in the table above were measured over the *other eight* artifacts, excluding this note.

## 4. Deliberate exclusions

| Excluded | From | Why |
|---|---|---|
| The `auth` schema | the drift table's scope | The census this plan consumes is `public`-schema only. An `auth` dump can carry role grants and inline keys into git history permanently, and `.planning/` is committed. |
| Row data | every artifact | AUDIT-02 is a schema question. No `SELECT *` was issued by this plan against anything. |
| The production hostname and project reference | every artifact | Never needed: production was read from a previously captured envelope, not contacted. |
| Function bodies | `db-diff.*.sql` | Not applicable — no diff was captured. Had one been, `--schema public` scoping plus this sweep would have been the control, since a function body is the classic carrier for an inline key. |
