# Redaction ledger — plan 01-12 (AUDIT-08, cache exposure)

**Written:** 2026-09-14
**Credential classes handled:** live session cookie sets (`COOKIE_A`, `COOKIE_B`), the production hostname (`PROD_HOST`), and the Supabase project ref that the deployment embeds in a `set-cookie` response header on some routes.

## 1. Where the credentials lived

| Value class | Where it lived during this plan | Ever on disk? |
|---|---|---|
| `COOKIE_A` / `COOKIE_B` | **Not supplied.** The operator did not export them, so the cross-session half of the probe did not run. No cookie value entered this machine's shell, let alone a file. | No |
| `PROD_HOST` | Passed to `cache-probe.sh` as a shell environment variable for the duration of the run. | Yes, deliberately — see §2 |
| Supabase project ref (`sb-<ref>-auth-token-code-verifier`) | Returned by production inside a `set-cookie` **response** header on `/api/health`. | No — replaced before the write, see §3 |

`cache-probe.sh` reads all three from `process.env` / `$VAR` only. No value is ever passed as a CLI argument (shell history), echoed, or logged, and the script never enables `set -x` — an acceptance criterion greps for it.

## 2. The production hostname is recorded, not redacted

`BLOCKING-INPUTS.md` §2 allows `PROD_HOST` to appear in the cache artifacts **if the operator confirms it is not sensitive**, and otherwise substitutes `<PROD-HOST>`. The operator supplied `universeapp.ca`, a public hostname that resolves from any DNS resolver and is served under a public TLS certificate. It is recorded verbatim in `cache/curl-summary.json` so the evidence is reproducible. The placeholder `<PROD-HOST>` is therefore **not** used in this plan.

## 3. What was replaced, where, and by what

| Artifact | Value class removed | Replaced with | Command that performed the substitution |
|---|---|---|---|
| `cache/curl/*.headers.txt` | Every `set-cookie` **response** header value | `<REDACTED>` | `sed -E 's/^([Ss]et-[Cc]ookie:).*$/\1 <REDACTED>/'`, inside the same pipeline that writes the file — an unredacted value never reaches disk, not even momentarily |

## 5. Finding candidates produced by this plan

One per `leak-confirmed` and `latent-hazard` row in `cache/cache-matrix.json`. Machine-readable source: the `finding_candidate` field on each matrix row. Evidence for every route is the capture set `cache/curl/<slug>.anon.{1,2,3}.headers.txt` plus the matching entries in `cache/curl-summary.json`.

### Critical — shared caching of a personalized response, proven on the wire (8 routes)

The blanket `Cache-Control: s-maxage=60, stale-while-revalidate=300` that `vercel.json` attaches to `/api/(.*)` **does** reach these personalized responses. Each returned `x-vercel-cache: HIT` or `STALE` with a non-zero `age`, and **no response varied on `Cookie` or `Authorization`** (`vary: accept-encoding` only) — so the stored entry is keyed by URL alone and is served to every caller of that URL regardless of which session produced it.

| Route | Observed cache states | Max `age` seen |
|---|---|---|
| `/api/notifications/count` | HIT, HIT, HIT | 43 s |
| `/api/events/following` | MISS, STALE, HIT | 96 s |
| `/api/events/friends-activity` | STALE, HIT, HIT | 77 s |
| `/api/events/friends-organizing` | STALE, HIT, HIT | 77 s |
| `/api/events/[id]/friends` | STALE, HIT, HIT | 77 s |
| `/api/events/[id]/rsvp` | STALE, HIT, HIT | 77 s |
| `/api/clubs/[id]/events` | STALE, HIT, HIT | 77 s |
| `/api/auth-debug` | STALE, HIT, HIT | 77 s |

Held at verdict `latent-hazard` rather than `leak-confirmed` **only** because the two-account observation was blocked — see §6. Proposed severity is Critical regardless: the mechanism is demonstrated, and the missing step is confirmation of the victim, not of the channel.

### High — auth-gated response under a session-independent shared-cache directive (37 routes)

Anonymous callers receive 401/403, so nothing was cached during this anonymous run. But the header is attached **by path**, not by response: the anonymous 401s on `/api/notifications` and `/api/users/saved-events` both carried `cache-control: s-maxage=60, stale-while-revalidate=300`, confirming the rule applies to the path irrespective of the auth outcome. An authorized caller's 200 on any of these paths is therefore storable and re-servable to an unauthorized one.

`/api/admin/analytics/events`, `/api/admin/analytics/users`, `/api/admin/audit-log`, `/api/admin/calculate-popularity`, `/api/admin/clubs`, `/api/admin/events`, `/api/admin/experiments`, `/api/admin/experiments/[id]`, `/api/admin/experiments/[id]/results`, `/api/admin/featured`, `/api/admin/organizer-requests`, `/api/admin/organizers`, `/api/admin/reports`, `/api/admin/stats`, `/api/admin/users`, `/api/calendar/events`, `/api/clubs/[id]/analytics`, `/api/clubs/[id]/follow`, `/api/clubs/[id]/invites`, `/api/clubs/[id]/members`, `/api/clubs/friends`, `/api/events/[id]/analytics`, `/api/events/[id]/reviews`, `/api/events/my-events`, `/api/moderation/reviews/[targetType]/[targetId]`, `/api/my-clubs`, `/api/notifications`, `/api/organizer-requests`, `/api/recommendations/analytics`, `/api/recommendations/feedback`, `/api/user/engagement`, `/api/user/following`, `/api/users/me/friends`, `/api/users/me/requests`, `/api/users/me/suggestions`, `/api/users/saved-events`, `/api/users/search`

### Not a finding, but Stage 3 must not lean on it

- `/api/recommendations` — `safe-by-design`. The handler sets `private, no-store` itself, which overrides the blanket header; observed `private, no-store` on the wire and `MISS` on all three requests. This is the pattern REFAC-19 should generalise.
- `/auth/callback` — `safe-by-accident`. It sits outside the `/api/(.*)` rule, so no shared-cache directive attaches. Nothing in the handler declares the response private; moving it under a header rule would expose it.
- `/api/health` — uncached only because it emits `set-cookie` on every response and the shared cache declines to store a cookie-setting response. Incidental, not designed.

## 6. What is BLOCKED and the exact command to unblock it

The **cross-session half** of AUDIT-08 did not run. `COOKIE_A` and `COOKIE_B` were not exported into the executing shell, and two distinct signed-in sessions are the only way to observe one account's response being served to another. Recorded as `BLOCKED — input not supplied` in `cache/curl-summary.json` under `cross_session_probe`.

```bash
export PROD_HOST=https://universeapp.ca
export COOKIE_A='<all sb-*-auth-token cookies, including numbered chunks, account A>'
export COOKIE_B='<the same for a different account B>'
export CLUB_ID='<a public club id>'   # optional; sharpens the /api/clubs/[id]/* rows
bash .planning/audit/tools/cache-probe.sh
node .planning/audit/tools/gen-cache-matrix.mjs
node .planning/audit/tools/validate.mjs --check cache
```

The probe refuses to run if `COOKIE_A` equals `COOKIE_B`, and degrades to the anonymous half rather than reporting a clean run when either is absent. When both are present, `gen-cache-matrix.mjs` promotes any row where a session-B request returns `HIT` from `latent-hazard` to `leak-confirmed` automatically.
