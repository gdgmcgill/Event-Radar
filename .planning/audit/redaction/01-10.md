## 1. How credentials were handled

**No credential of any kind entered this machine's shell environment during this plan, and this plan opened no network connection.**

Continuing the resolution recorded in `01-06-SUMMARY.md` and `redaction/01-06.md`, and followed unchanged by plans 01-08 and 01-09: production was read **once**, by the orchestrator, through the authenticated **Supabase MCP server** (Management API), SELECT-only, as role `postgres`, and those reads were committed as capture envelopes under `.planning/audit/raw/prod/`. This plan consumed **only those committed envelopes from local disk**.

| | Planned path (01-10 PLAN.md, Tasks 1 and 3) | Path actually used |
|---|---|---|
| Database transport | `tools/sql-readonly.mjs` → Management API, per query | `raw/prod/*.json`, already on disk, read with `fs.readFileSync` |
| Deployment-platform transport | a human reading the Vercel dashboard and pasting the result | `raw/vercel/*.json`, captured by the orchestrator through the Vercel REST API before this plan began — see § 3 |
| Credential material held by this plan | `SUPABASE_ACCESS_TOKEN`, or a `postgres://` URI, or a Vercel token | none — no credential was needed or present |
| Network connections opened by this plan | 5 | **0** |
| Could a credential reach an artifact? | yes, via an error object, a pasted dashboard value, or a traced command | no — none existed in the environment |

Specifics, stated because they govern the next pass as much as this one:

- `SUPABASE_ACCESS_TOKEN`, `PROD_PROJECT_REF`, `STAGING_PROJECT_REF`, `SUPABASE_DB_PASSWORD`, `PROD_DB_URL`, `STAGING_DB_URL`, `VERCEL_TOKEN`, `CRON_SECRET` and `WEBHOOK_SECRET` were **unset for the duration of the plan**. No secret was passed as a command-line argument, because no command in this plan took one.
- **No shell tracing.** `set -x` was not enabled at any point. `tools/readonly-guard.sh` carries an explicit comment forbidding it in this phase; plan 01-09 recorded a single traced verification block and the reason it was harmless, and this plan did not repeat it.
- **No new tool was added under `tools/`.** The plan's `files_modified` list does not include one, and the phase's read-only rule is that only the listed paths are created. The two derivations this plan performs — the bucket/policy artifacts and the scheduled-job artifacts — were generated by scripts held **outside the repository**, in the session scratchpad, reading committed envelopes and writing only into `.planning/audit/`. Those scripts read no environment variable and opened no socket. Their content is reproduced as the `node -e` one-liners in § 6 of `storage/storage-review.md` and § 8 of `async/cron-webhook-inventory.md`, so every number in both documents is re-derivable from the committed inputs without them.
- **No package manager was invoked.** Only Node built-ins (`node:fs`) were used. `package.json` and `package-lock.json` are byte-identical; asserted by `tools/readonly-guard.sh` check 2 after every task.
- **No write of any kind reached the database, the storage buckets, or the deployment platform.** This plan issued no SQL, uploaded/downloaded/listed/deleted no storage object, and ran no `supabase` or `vercel` CLI command. **No production HTTP endpoint was contacted** — in particular neither `/api/cron/*` handler was probed, because probing an authorization gate to see whether it is open is itself an unauthenticated write attempt against production. Their credential posture in `async/cron-webhook-inventory.md` is read from source and cross-referenced to `authz/fail-open-register.md`, which is the only sound way to answer that question in a read-only phase.

## 2. The value class this plan was most likely to leak, and why it did not

Two, and they are different from the ones the earlier plans guarded.

**A webhook secret.** `supabase/functions/events-webhook/index.ts` reads `WEBHOOK_SECRET` and uses it as an HMAC key. The inventory names the variable, describes where it is read and what happens when it is absent, and **never records a value**; the sweep in § 6 carries a dedicated `WEBHOOK_SECRET\s*[=:]\s*[A-Za-z0-9]` pattern for exactly this shape. `supabase/functions/.env.example` was **not** copied into any artifact.

**A `return_message` from a scheduled-job failure.** `cron.job_run_details.return_message` carries whatever Postgres emitted, which for a failing function can include a fragment of the failing statement — the classic accidental carrier for an inline literal. It was retained rather than dropped, because a run history without its error text answers the wrong question, and then checked exhaustively instead of spot-checked: the captured 100 rows contain exactly **one distinct value**, the string `1 row`, on every row. There is no error text in this capture to leak. Verified by set-reducing the column rather than by eye:

```bash
node -e "const r=JSON.parse(require('fs').readFileSync('.planning/audit/async/cron-job-run-details.json','utf8'));console.log([...new Set(r.map(x=>String(x.return_message)))])"
# [ '1 row' ]
```

## 3. The Vercel capture — a transport deviation, recorded rather than smoothed over

`01-10-PLAN.md` Task 2 is a `checkpoint:human-action` asking an operator to read the project's Cron Jobs page and paste the result. **That is not how the answer was obtained.** Before this plan ran, the orchestrator captured the same state through the **Vercel REST API** with a read-only CLI login token, and committed two envelopes under `.planning/audit/raw/vercel/`. The checkpoint was therefore treated as already resolved, and `async/vercel-crons.md` transcribes the API answer with its provenance instead of a dashboard screenshot.

This is a deviation of the same class as the one 01-06 recorded for the database transport, and it is recorded here for the same reason: the artifact must say where its evidence came from, because the two sources have different failure modes. The API answer is **stronger** than the one the checkpoint asked for — it is a machine-readable field with a capture timestamp rather than a human's reading of a page — and it is the reason the plan could complete without a human in the loop.

**What the capture could have leaked, and did not.** `GET /v9/projects/{id}/env` returns environment variable **values** in its response body. The orchestrator selected `key`, `target` and `type` only and discarded the values without logging them; the committed envelope's `fields` line states this on its face. No value appears in `raw/vercel/env-names.json`, in `async/vercel-crons.md`, or in `async/cron-webhook-inventory.md`, and the inventory's central cross-reference — which names are configured in production against which names the code reads — is a question about **names**, which is exactly why it can be answered in a committed artifact at all.

Two identifiers do appear in the committed envelope and in the artifacts derived from it, and both are deliberate rather than overlooked:

| Value | Where | Why it is not redacted |
|---|---|---|
| The Vercel project id (`prj_…`) and deployment ids (`dpl_…`) | `raw/vercel/project.json` | Opaque resource identifiers, not credentials. They confer no access; every Vercel API call that uses one still requires a token. They are the only way a later pass can confirm it is reading the same project. |
| The GitHub org and repository name | `raw/vercel/project.json` | Already public in the repository's own remote. |

Neither matches a `REDACTION.md` sweep pattern, and neither is on the placeholder table.

**The Supabase project reference is not in any artifact this plan writes.** `raw/prod/MANIFEST.json` stores it as `<PROD-PROJECT-REF>`, and nothing in this plan needed it.

## 5. Command and expression literals, inspected specifically

Two artifacts carry executable text, and both were enumerated rather than skimmed.

**Scheduled-job commands** — all three, in full: `select public.send_event_reminders()`, `SELECT compute_user_scores()`, `SELECT public.send_feedback_requests()`. Three bare, zero-argument function calls. No literal of any kind, no URL, no header, no key. Notably **none of them issues an HTTP request** — there is no `net.http_post(...)` carrying an `Authorization` header, which is the single most common way a cron secret ends up committed in a `cron.job` capture. `pg_net` is not installed (`async/extensions.json`), so that shape is not merely absent here, it is unavailable in this project.

**Storage policy expressions** — the 15 rows in artifact 2 are a subset of the 101 rows plan 01-09 captured, and § 4 of `redaction/01-09.md` already enumerated every string literal across all of them. Re-derived over this plan's subset for completeness: `'authenticated'`, `'service_role'`, `'banners'`, `'club-logos'`, `'event-images'`. Three of those are bucket names and two are Postgres role names. **None is a credential, a key, a token, a URL, or a personal identifier**, and no scrub was performed on any expression because none carried a value requiring one.

### The sweep was run under `bash`, with an array — deliberately

```bash
bash -c 'FILES=(.planning/audit/storage/buckets.json … .planning/audit/async/cron-webhook-inventory.md)
PATTERNS=( … the fourteen above … )
for p in "${PATTERNS[@]}"; do tot=0
  for f in "${FILES[@]}"; do c=$(command grep -cE "$p" "$f" || true); tot=$((tot+c)); done
  printf "%s %s\n" "$p" "$tot"
done'
```

Plan 01-08 recorded a false-clean caused by running exactly this loop under `zsh`, where an unquoted `$FILES` holding a space-separated path list does **not** word-split: the loop passes one long non-existent path and prints `0` for every pattern. Plan 01-09 recorded the same control. Both were applied again here:

1. The sweep ran from a script file under `bash`, with a real array, never an unquoted variable holding a path list.
2. **A positive control was run alongside it.** Over the storage artifacts the control patterns `bucket_id` and `auth\.uid` returned **20** and **13**. Over the asynchronous artifacts the control patterns `jobname` and `send_event_reminders` returned non-zero. A zero count is only evidence if the command that produced it was capable of producing a non-zero one.

## 7. Deliberate exclusions

"Excluded" means *never captured in the first place*, which is the only exclusion that is safe once `commit_docs` is `true` and the artifact is in git history permanently.

| Excluded | From | Why |
|---|---|---|
| Every environment variable **value** | all artifacts | The Vercel API response carried them; they were discarded unread at capture time. The census in the inventory is a question about names. |
| Stored object contents, names and listings | the storage artifacts | AUDIT-18 asks about buckets and policies. Listing objects would put user-uploaded filenames — which include user ids and club ids by construction — into git permanently, and would answer nothing the catalog does not. |
| The Supabase project reference and the production hostname | all artifacts | Never needed. Production was not contacted by this plan. |
| Function **bodies** | all artifacts | `raw/prod/functions.json` carries full `pg_get_functiondef` text and was read to establish what the three scheduled jobs actually do. Their behavior is **described** in the inventory; no body was copied into an artifact. A function body is the classic carrier for an inline key. This follows `redaction/01-09.md` § 5 unchanged. |
| `supabase/functions/.env.example` | all artifacts | Names the webhook secret. Not copied, not quoted, not needed. |
| Live probes of `/api/cron/*` | all artifacts | See § 1. A probe is a write attempt, and its response would have to be recorded. |
