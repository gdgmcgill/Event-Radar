PROVENANCE — THIS IS NOT `supabase migration list` OUTPUT
---------------------------------------------------------
The command the plan specifies is:

    supabase migration list --linked   > .planning/audit/schema/migration-list.prod.txt
    # or, without linking:
    supabase migration list --project-ref "$PROD_PROJECT_REF"
    # or, with a direct connection:
    supabase migration list --db-url "$PROD_DB_URL"

None of those could run. `--linked` requires `supabase link`, which writes project
state into supabase/.temp/ — a write inside the directory under audit, forbidden by
this phase. `--project-ref` requires SUPABASE_ACCESS_TOKEN and `--db-url` requires a
connection string; per .planning/audit/redaction/01-06.md § 1 neither was ever supplied.

The REMOTE column below is nonetheless real production data. It was read in plan 01-06
through the authenticated Supabase MCP server (Management API `list_migrations`), which
reads the same table `supabase migration list` reads — supabase_migrations.schema_migrations.
The captured envelope is:

      captured_at: 2026-09-14T18:32:38Z

(see migration-list.local.txt and schema/local-reset.txt). It is the set of versions

WHAT THE REMOTE-ONLY VERSIONS ARE
---------------------------------
All 18 are bare timestamps with no name recorded — the shape the Supabase dashboard SQL
editor writes when DDL is run there, and the shape `supabase db push` writes for a
migration whose file has since been deleted. The Management API returns only `version`
for these rows (the envelope's rows each carry a single key), so the statements they
applied are not recoverable from the history table alone. Seventeen of the eighteen fall
in 2026-03-15/16, one on 2026-03-24 — i.e. production received a burst of out-of-band
schema changes that the repository never saw. The columns they created are visible in the
production census, and drift.json marks them prod-only.
