Note for whoever fills this gap: 01-RESEARCH.md § Assumptions Log A4 records that
PROJECT.md asserts a staging project exists, but that this was never verified in
session. "Not now" is a scheduling answer, not a statement that staging is absent.
If it turns out no staging project exists at all, that is itself an AUDIT-02 finding —
a two-environment promotion story documented as a three-environment one, with no
staging gate between the repository and production — and should be filed rather than
recorded here as a deferral. The 18 remote-only versions in migration-list.prod.txt
are circumstantial support for that reading: schema changes that reached production
without passing through any migration file would, in a working three-environment
promotion flow, have had to clear staging first.

TO PRODUCE A REAL LIST
----------------------
Run from the repository root with the credential exported into the shell only — never
written to a file, never passed as a command-line argument:

    export SUPABASE_ACCESS_TOKEN=...            # in the shell only
    supabase migration list --project-ref "$STAGING_PROJECT_REF" \
      > .planning/audit/schema/migration-list.staging.txt

    # direct-connection fallback, when no access token can be issued
    supabase migration list --db-url "$STAGING_DB_URL" \
      > .planning/audit/schema/migration-list.staging.txt

    bash .planning/audit/tools/readonly-guard.sh

Do NOT use `supabase link --project-ref "$STAGING_PROJECT_REF"` followed by `--linked`.
`link` writes project state into supabase/.temp/, which is inside the directory this
phase is auditing; the per-command `--project-ref` form avoids that write entirely.

CONSEQUENCE FOR AUDIT-02
